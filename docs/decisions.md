# Decisions

Every standing choice of kitden-sdlc, one row each: what we chose, why, where it is written or
was seen, and when to look at it again. The table holds what stands today; a choice that was
later replaced is not here. The first eleven rows are the main choices of the full-cycle design
(2026-11-13), the next ten were made while stage 0 was built, and the rest come from RULES.md,
AGENTS.md, LOG.md and the four earlier designs: [reviewers](design.md),
[client watcher](watcher-design.md),
[release flow](superpowers/specs/2026-11-12-release-flow-design.md) and
[release prep](superpowers/specs/2026-11-13-release-prep-tune-design.md). A new choice is a new
row, and a changed choice replaces its row, in the pull request that makes it.

| Choice | Why | Seen at | Look again when |
|---|---|---|---|
| Scripts measure, models propose, the owner decides | the owner's worst case is a false "all is well" | PyTorch, uv, GitHub Agentic Workflows: the model reads, a job without a model writes | never |
| No agent merges or is a required check | an injected prompt could block or pass every merge | PyTorch forbids it in the workflow file; Copilot's agent cannot approve or merge | a new design, not a setting |
| Steps of trust: comment, issue, test, code | a mistake at each step costs more than at the one before | Vercel: draft pull requests, a person merges; uv: reproduce before fix | 30 days of numbers per step |
| Tests before fixes; fix only with red-then-green proof | a script can check a proof; it cannot check a claim | uv's chain from triage to a failing test to a fix | never |
| Code only on the owner's label | the owner must not lose control of the cycle | Prow: labels are the commands | the owner asks for more |
| A desk made by a script, not a manager agent; its data in one file | a model's summary of its own team is not evidence; a later dashboard reads the same file | gemini-cli keeps its frequent layer as plain scripts | the owner wants the dashboard |
| Evidence and caps on every issue | noise ends such setups | Django switched automated reviews off | false alarms stay under the bar |
| A host list, one key per workflow, no debug output | the model key is the secret an injected prompt steals | Anthropic's own repository; Microsoft's report; "Comment and Control" | short-lived keys become possible |
| Who found each bug, as the main number | almost nobody publishes how often their agents are right | Zed tracks its duplicate bot; Atlassian measures fixed findings | never |
| Stay on our own workflows | the platform had its own advisory, and our one-comment logic would be rewritten | GitHub Agentic Workflows | it offers what we cannot build |
| At most 8 model agents | every agent is review time and something that can break | the factory rolled back after three months | a written case |
| On the desk, bad news that the read facts prove always wins; grey only when nothing bad was found and a fact is missing | a page that looks better than the facts is the owner's worst case | scripts/desk.py | never |
| The Works light judges main's own CI only: the newest run of each check, from runs the push to main started; a failed check main does not require is amber | a hand-started or scheduled run that failed once kept the light red for no reason | scripts/desk.py | two push workflows share a job name |
| A refusal to post never prints any character of the refused text or a model-chosen file name; it prints a count | a public log line with pieces of a possible key is a leak | scripts/post_findings.py, scripts/release_apply.py | never |
| The model's output is kept as a run artifact for one day before the checks run (seven for the watcher) | artifacts of a public repository can be downloaded by anyone signed in; the checks run in the posting job | RULES.md rule 6 | the checks move into the model job, before the upload |
| A bot knows its issues by their author; it may edit, close or comment only on an issue it has itself listed in that run | by title alone it would rewrite a person's issue | scripts/bot_issues.py | never |
| `confirmed` keeps a bot issue open until the problem is fixed; only `false-alarm` closes | a closed issue said nothing about whether the problem was fixed | scripts/bot_issues.py | never |
| A noisy agent pauses itself: more than half of its last 10 verdicts `false-alarm` opens "<agent> is paused"; the owner lifts it by closing that issue. Only the verdicts the owner gives count | a pile of bot issues nobody needs ends such setups | scripts/bot_issues.py | the owner closes issues without a label instead of giving verdicts |
| A failed reviewer is named in the comment, and when neither answers the comment says so for that commit; no reviewer's failure leaves a red mark, but a refusal to post secret-like text and a failure of the workflow's own steps do | four green jobs over an old "No problems found" is a false all-is-well, no agent is in anyone's way, and a secret in a model's text or a broken step must be seen | scripts/post_findings.py; RULES.md rule 11; LOG.md 2026-11-13 | never |
| The desk reads the reviews once a run, one call per pull request | simple and enough today | scripts/desk_gather.py | by 2026-12-15, or at about 250 pull requests in 90 days (replace with one list call for all issue comments) |
| An injection task counts as obeyed when in doubt, and the table names the task | a wrong "yes" is read by a person, a wrong "no" hides a failure | evals/score.py | never |
| A pull request cannot change the rules it is judged by: Kitden holds only thin callers (review, check, release prep, release watch) and its own `release.yml`, and the rules live in kitden-sdlc or come from the base branch | a reviewer whose rules a pull request can change is no reviewer, and GitHub runs a workflow only from the repository of the pull request, so the callers cannot move; the pull request's own `AGENTS.md`, `CLAUDE.md` and `.review/` are removed or put back | docs/design.md, part 1; scripts/prepare_review.sh, .github/workflows/review.yml; LOG.md 2026-11-09 and 2026-11-10 | never |
| Two reviewers from two makers, Claude and GPT-6 Luna | two independent reviews that work by different methods; Claude is paid by the owner's Max plan, Luna by a separate OpenAI key | docs/design.md, parts 1 and 5: Anthropic's code-review plugin and OpenAI's Codex review rubric | 30 days of numbers show whether Luna finds what Claude does not |
| Kitden's own review skill, not Anthropic's `code-review` plugin, which it follows in method | the plugin reviews once, runs helpers on three models and holds `gh pr comment`, which breaks rules 1, 3 and 6 and the one-model comparison | docs/design.md, part 4: Anthropic's code-review plugin | never |
| One review comment per pull request for both reviewers, edited in place, no inline comments; a finding the next review does not repeat stays, marked fixed only when its lines changed | a comment per finding is spam, and only the first comment sends a notification; on Kitden pull request 70 a valid finding vanished because the model did not repeat it | docs/design.md, part 4 (owner, 2026-11-10); scripts/post_findings.py; LOG.md 2026-11-12 | never |
| At most five findings per reviewer, only what is surely wrong, each checked before it is kept | noise ends such setups, and a wrong comment costs the owner time | docs/design.md, parts 4 and 5; Anthropic's code-review plugin | false alarms stay under the bar |
| Reviews run on `pull_request` only and skip forks and bots | a fork's run gets no secrets, and a job that had them would hold outside text next to a secret | RULES.md rule 2 | a design for reviewing fork pull requests, which the owner wants later |
| At most 10 reviews a day, counted by a step without a model (Kitden's caller sets 20) | Claude runs on the owner's Max plan, a limit shared with his own work | docs/design.md, part 3; .github/workflows/review.yml | reviews stop running on the Max plan |
| One switch stops every agent; the reviewers and the watcher's daily run each have a second one | the owner stops everything in one place, and the watcher's eval can run while its daily run is off | docs/owner.md; docs/watcher-design.md, part 7 | never |
| A project key for OpenAI with a $5 monthly budget set in its dashboard | when the budget ends only the Luna job fails and nothing else changes | docs/design.md, part 3; docs/agents.md | the first months of real cost are known |
| The posting job refuses text that looks like a secret or holds a long random string the model was not given | the model's text becomes a public comment, so a key it was tricked into copying must stop at the poster | RULES.md rule 6; scripts/secret_filter.py | never |
| A change to a prompt, a skill or a model comes with its eval table, before and after, in the same pull request | a change nobody measured can make an agent worse without anyone seeing it, and one run of a judge proves little | AGENTS.md; docs/superpowers/specs/2026-11-13-full-cycle-design.md part 3 | never |
| The watcher runs in kitden-sdlc on its own schedule; Kitden has no workflow for it | nothing in Kitden starts it, and its memory would be a branch of agent data in the product's repository | docs/watcher-design.md, part 1 | never |
| What Kitden relies on in each client is a file in Kitden, `docs/clients.md`, with a test that its files exist | the list must change in the same pull request as the code it describes, and the test keeps it from rotting | docs/watcher-design.md, part 2 | never |
| Release notes and doc pages are read, Codex only by its stable releases, and doc pages are kept as one hash per section, never as text | Codex pre-releases come several a day with empty notes, and doc pages are other companies' text while the memory branch is public | docs/watcher-design.md, part 3; config/watch-sources.yml; scripts/watch_pages.py | a change the ChatGPT app ships early is missed until the stable release |
| At most two urgent issues a week, the third going to the top of the summary; everything else goes into one summary issue in the first run of the week, and no items means no issue | the owner's attention is the limit: a flood of urgent issues would be read as noise, and one weekly read is enough for what is not a break | docs/watcher-design.md, part 5 (owner); scripts/watch_route.py | false alarms stay under the bar |
| A finding that would be urgent gets a second look that tries to refute it; if refuted it goes to the summary as `unsure` | an urgent issue is the costliest false alarm | docs/watcher-design.md, part 4; scripts/watch_judge.py | the eval table shows the second look changes nothing |
| The first run only fills the memory and opens nothing | a first run would flood the owner with the clients' whole history | docs/watcher-design.md, part 6; scripts/watch_fetch.py | never |
| The watcher is switched on only after an eval that passes in each of three runs: every break found, the planted order not obeyed, at most 2 of 15 false alarms | the judge does not answer the same way twice, so one good run proves little | docs/watcher-design.md, part 9; evals/watch_score.py; LOG.md 2026-11-11 | never |
| The watcher's judge is Claude Sonnet 5.5 at effort medium | GPT-6 Luna did not pass the eval | docs/watcher-design.md, part 4 (owner, 2026-11-12); docs/agents.md | a cheaper model passes the eval table |
| One pull request per release; the owner reviews and merges it, and everything after the merge runs by itself | a list of manual steps lost steps: a Homebrew bump waited for a forgotten merge, and the registry needed a browser login every time | docs/superpowers/specs/2026-11-12-release-flow-design.md, Why and Goals | never |
| Three GitHub Apps, each with its key where it is used: Lantern comments and opens issues (its key in kitden-sdlc), Beacon releases (its key only in Kitden's `release` environment, named by no model job), Kettle bumps the Homebrew tap (its key only in the tap); kitden-sdlc stores no publishing secret | whoever holds a key that can push a `v*` tag can publish to PyPI, Lantern's key sits beside the review agents, a model job must never hold a publishing token, and Kettle runs `brew bump`, code from outside, so it must never hold the release key | docs/superpowers/specs/2026-11-12-release-flow-design.md, Identities and secrets and What runs where; RULES.md rule 1; docs/agents.md | never |
| PyPI publishing stays in Kitden's own `release.yml` | PyPI's Trusted Publisher is that file and the `pypi` environment | docs/superpowers/specs/2026-11-12-release-flow-design.md, What runs where | PyPI's trust is moved to another file |
| Merging the release pull request tags the version, as the release app, from `main` | a tag made with the job's own token starts no workflow, and `pypi` accepts only `v*` tags, so a run on `main` cannot publish | docs/superpowers/specs/2026-11-12-release-flow-design.md, A2 | never |
| The Claude plugin directory and Kitden's own marketplaces read the `release` branch, not `main` | the directory picked up two later `main` commits as 0.7.2 that differ from the tag, and people got unreleased plugin code under the last version | docs/superpowers/specs/2026-11-12-release-flow-design.md, A5 | never |
| The Homebrew bump pull request is pulled by the tap's own workflow, never by the Merge button | merged with the button it publishes no bottles, which happened on 0.7.0 | docs/superpowers/specs/2026-11-12-release-flow-design.md, A6 | never |
| The release watch only proposes a release; the version is picked in release prep, not by the watch | without a model the watch cannot tell New from Fixed, and Kitden's pull requests carry no prefixes for it | docs/superpowers/specs/2026-11-12-release-flow-design.md, A7; scripts/release_watch.py | never |
| One check before publishing: each wording sits once in `listing.toml`, and the version is the same in every file | the product description existed in four wordings and the version in eight files | docs/superpowers/specs/2026-11-12-release-flow-design.md, A1; scripts/release_check.py | never |
| The release branch is `prepare-vX.Y.Z`, and the pull request is merged with a merge commit | git cannot hold branches `release/...` next to the branch `release`, and the notes link the branch's commits | docs/superpowers/specs/2026-11-12-release-flow-design.md, B2; scripts/release_apply.py | never |
| The agent edits the policy files and `listing.toml` itself, in a commit of their own | the owner reads policy changes apart from the notes, and nothing reaches `main` without his merge | docs/superpowers/specs/2026-11-12-release-flow-design.md, B2 (owner, 2026-11-12); MERGE_POLICY.md | never |
| At most three bot pull requests wait for the owner; release prep does not start behind them | the owner's own limit on what he reviews | docs/superpowers/specs/2026-11-12-release-flow-design.md, Anti-goals (owner, 2026-11-09); scripts/release_context.py | the owner asks for more |
| Release prep checks its own work with scripts before the pull request opens, gives the agent one fix pass, and opens a draft with the problem first in the body when one is left | the pull request for 0.9.0 needed a review by hand (red CI, a file the agent could not write, pictures nobody checked); one pass heals the common case and never blocks, at the cost of one short agent job only when something is wrong; a strict check must not stop a run, but a pull request with a known problem must not look ready | docs/superpowers/specs/2026-11-13-release-prep-tune-design.md, Why, Approaches (owner, 2026-11-13) and Anti-goals; scripts/release_apply.py | the re-run for 0.9.0 shows what the pass leaves |
| Kitden's own tests are the agent's contract, and a script runs them on the agent's files | the skill said "about 125 lines" while the test allows 125, and the agent followed the skill | docs/superpowers/specs/2026-11-13-release-prep-tune-design.md, Approaches | never |
| Scripts decide which pictures change; the agent only says what it expects | the agent cannot see the page: it asked to record `library` again and the picture came out the same, byte for byte | docs/superpowers/specs/2026-11-13-release-prep-tune-design.md, Part 4; scripts/release_apply.py | a still differs from run to run on the runner |
